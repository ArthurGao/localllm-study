RAG 技术深度知识库
==================

第一章：RAG 架构演进

1.1 Naive RAG（朴素 RAG）

Naive RAG 是最基础的 RAG 实现，流程简单直接：
用户提问 → 向量检索 → 拼接上下文 → LLM 生成答案。

Naive RAG 的主要局限：
- 检索质量完全依赖 Embedding 模型和分块策略
- 没有查询优化，用户措辞不同可能导致完全不同的检索结果
- 没有结果验证，可能将不相关的文本块送入 LLM
- 单次检索，无法处理需要多步推理的复杂问题

1.2 Advanced RAG（高级 RAG）

Advanced RAG 在 Naive RAG 的基础上增加了预检索和后检索优化：

预检索优化（Pre-Retrieval）：
- 查询重写（Query Rewriting）：让 LLM 将模糊查询改写为更精确的搜索词
- HyDE（假设文档嵌入）：先生成假设答案，用假设答案去检索
- Multi-Query（多查询）：将一个问题改写为多个变体，分别检索后合并
- 查询分解（Query Decomposition）：将复杂问题拆分为多个子问题

后检索优化（Post-Retrieval）：
- 重排序（Reranking）：用 Cross-Encoder 对检索结果精确打分重排
- 上下文压缩（Contextual Compression）：去除检索结果中的冗余信息
- 融合检索（Hybrid Search）：结合向量检索和 BM25 关键词检索

1.3 Modular RAG（模块化 RAG）

Modular RAG 将 RAG 系统拆分为可插拔的模块：
- 路由模块（Router）：根据问题类型选择不同的检索策略
- 反馈循环（Feedback Loop）：根据答案质量自动调整检索参数
- Agentic RAG：使用 AI Agent 动态决定何时检索、检索什么

第二章：Embedding 技术详解

2.1 什么是 Embedding

Embedding（嵌入）是将离散的文本数据映射到连续的向量空间中的技术。
核心目标：语义相似的文本在向量空间中距离更近。

数学表示：
文本 T → Embedding 模型 → 向量 v ∈ R^d（d 维实数向量）

例如：
"机器学习" → [0.23, -0.87, 0.45, ..., 0.12]  (768维)
"深度学习" → [0.25, -0.89, 0.43, ..., 0.11]  (语义相近，向量接近)
"烹饪方法" → [-0.54, 0.32, -0.71, ..., 0.88] (语义不同，向量远离)

2.2 Embedding 模型对比

nomic-embed-text：
- 维度：768
- 最大 Token：8192
- 特点：Ollama 原生支持，本地部署首选
- MTEB 得分：约 62

text-embedding-3-small（OpenAI）：
- 维度：1536
- 特点：性价比高，每百万 token $0.02
- MTEB 得分：约 62.3

BGE-M3：
- 维度：1024
- 特点：支持 dense + sparse + multi-vector 三种检索方式
- 适合需要混合检索的企业场景
- MTEB 得分：约 63.0

2.3 相似度度量方式

余弦相似度（Cosine Similarity）：
- 计算两个向量夹角的余弦值
- 范围：[-1, 1]，1 表示完全相同，0 表示正交
- 最常用，不受向量长度影响

欧氏距离（Euclidean Distance）：
- 计算两个向量之间的直线距离
- 范围：[0, ∞]，0 表示完全相同
- 适合绝对位置重要的场景

内积（Dot Product）：
- 直接计算两个向量的点积
- 受向量长度影响，向量归一化后等价于余弦相似度

第三章：向量数据库深度对比

3.1 ChromaDB

ChromaDB 是为 AI 应用设计的开源向量数据库。

核心特性：
- 零配置，pip install 即可使用
- 支持持久化到本地磁盘
- 内置 Embedding 函数
- 支持元数据过滤（Metadata Filtering）
- 与 LangChain、LlamaIndex 深度集成

使用场景：本地开发、原型验证、中小规模应用（< 100万向量）

限制：
- 不支持分布式部署
- 没有内置的高可用方案
- 大规模数据性能不如专业向量数据库

3.2 Pinecone

Pinecone 是云托管的向量数据库服务。

核心特性：
- 全托管，无需运维
- 自动扩展
- 支持命名空间（Namespace）隔离
- 毫秒级查询延迟

使用场景：生产环境、需要高可用和自动扩展的应用

限制：
- 按用量收费，大规模使用成本较高
- 数据存储在云端，不适合对数据隐私要求极高的场景

3.3 Qdrant

Qdrant 是用 Rust 编写的高性能向量数据库。

核心特性：
- 高性能，Rust 实现
- 支持 payload 过滤（条件过滤 + 向量检索）
- 支持分布式部署
- 提供 gRPC 和 REST API

使用场景：中大规模生产环境（百万到十亿级向量）

3.4 FAISS

FAISS（Facebook AI Similarity Search）是 Meta 开源的向量搜索库。

核心特性：
- 纯计算库，不是数据库
- GPU 加速支持
- 多种索引类型（Flat、IVF、HNSW、PQ）
- 极高的查询性能

使用场景：超大规模向量搜索（十亿级）、对性能有极致要求

限制：
- 没有内置持久化
- 没有分布式支持
- 需要自行管理数据存储

第四章：分块策略实战

4.1 分块对检索效果的影响

分块策略是 RAG 系统中最容易被忽视但影响最大的因素。

实验数据（2024年基准测试）：
- 512 token 递归分块 + nomic-embed-text → 69% 召回率
- 256 token 固定分块 + nomic-embed-text → 58% 召回率
- 1024 token 固定分块 + nomic-embed-text → 52% 召回率
- 语义分块 + nomic-embed-text → 67% 召回率

结论：512 token 的递归分块是大多数场景的最佳起点。

4.2 中文分块的特殊考虑

中文文本的分块需要注意：
1. 中文没有空格分隔单词，字符数和 token 数的比例与英文不同
2. 中文句号是"。"而不是"."，需要在分隔符列表中特别处理
3. 段落之间通常用空行分隔
4. 建议的中文分隔符优先级：["\n\n", "\n", "。", "！", "？", "，", " ", ""]

4.3 Overlap 重叠的作用

Overlap（重叠）确保关键信息不会在块边界被截断。

例如：原文"RAG 的核心是检索增强。这种技术可以减少幻觉。"
- 无重叠：块1="RAG 的核心是检索增强。"，块2="这种技术可以减少幻觉。"
  → "这种技术"在块2中缺乏上下文，不知道指的是什么
- 有重叠：块1="RAG 的核心是检索增强。"，块2="检索增强。这种技术可以减少幻觉。"
  → "这种技术"有了前文，语义完整

推荐的 overlap 设置：chunk_size 的 10%-20%

第五章：Prompt 工程最佳实践

5.1 RAG Prompt 设计原则

好的 RAG Prompt 应该：
1. 明确角色定位：告诉模型它是一个基于文档的问答助手
2. 提供清晰的上下文标记：让模型知道哪部分是检索到的参考资料
3. 设置回答约束：只能基于上下文回答，不能编造
4. 处理信息不足的情况：当上下文中没有答案时，应该说"不知道"

5.2 常见 Prompt 模式

模式一：严格约束型
"请严格根据以下参考资料回答。如果资料中没有相关信息，请回答'无法找到相关信息'。"

模式二：引用来源型
"请根据参考资料回答，并在回答中标注信息来源。格式：[来源1] xxx [来源2] yyy"

模式三：推理分析型
"请根据参考资料回答。如果资料中有部分相关信息，可以在此基础上进行合理推理，但需要明确标注哪些是直接来自资料，哪些是推理。"

5.3 Temperature 对 RAG 的影响

在 RAG 任务中，temperature 的选择至关重要：
- temperature=0.0：最确定性的输出，适合事实性问答
- temperature=0.1：略有变化，推荐用于大多数 RAG 场景
- temperature=0.3：适度创造性，适合需要综合分析的问题
- temperature=0.7+：高创造性，不建议用于 RAG（容易产生幻觉）

第六章：RAG 评估指标

6.1 检索质量指标

召回率@K（Recall@K）：
在 Top-K 检索结果中，包含正确答案的比例。
Recall@3 = 0.7 表示 70% 的问题能在前3个检索结果中找到答案。

精确率@K（Precision@K）：
Top-K 检索结果中，有多少是真正相关的。
Precision@3 = 0.5 表示前3个结果中平均只有1.5个是相关的。

MRR（Mean Reciprocal Rank，平均倒数排名）：
第一个正确结果出现位置的倒数的平均值。
例如正确答案分别排在第1、3、2位：MRR = (1/1 + 1/3 + 1/2) / 3 = 0.61

6.2 生成质量指标

忠实度（Faithfulness）：
答案中的每个陈述是否都能在检索到的上下文中找到依据。
低忠实度意味着模型在"编造"信息。

答案相关性（Answer Relevancy）：
生成的答案是否真正回答了用户的问题。
即使答案基于上下文但偏题，相关性也会很低。

6.3 端到端指标

答案正确性（Answer Correctness）：
与人工标注的标准答案进行比较，衡量语义一致性。
通常使用 Embedding 相似度 + 关键词匹配来计算。

第七章：LangChain 核心概念

7.1 Document 对象

LangChain 中的 Document 是文本数据的基本单位：
- page_content：文本内容
- metadata：元数据字典，包含来源、页码、作者等

7.2 Retriever 接口

Retriever 是 LangChain 的检索抽象：
- 输入：查询字符串
- 输出：Document 列表
- 常见实现：VectorStoreRetriever、BM25Retriever、EnsembleRetriever

7.3 Chain 链

Chain 是 LangChain 的核心组件，将多个步骤串联：
- RetrievalQA：检索 + 问答链
- ConversationalRetrievalChain：支持多轮对话的检索链
- LCEL（LangChain Expression Language）：更灵活的链式组合语法

7.4 num_ctx 参数的重要性

在使用 Ollama 时，num_ctx（上下文窗口大小）是一个关键参数：
- 默认值通常是 2048，对于 RAG 来说太小了
- RAG 场景建议设置为 8192 或更大
- 如果 num_ctx 太小，检索到的文档会被截断，导致答案不完整
- Qwen3:8b 支持最大 32768 的上下文窗口
